Embarko API

The multi-tenant management API: companies, projects, deployments, environment variables, deploy tokens, custom domains, billing, and analytics. This is what the dashboard frontend talks to for every screen except the actual "deploy is running" build log.

JSON over HTTPS Single credential: proxy_auth_token header Pre-launch — no public URL yet
Local dev
http://localhost:4100
Production
api.embarko.ai (not yet public)
Not yet reachable from outside — flag to backend if you need a staging URL.

Auth model

This changed since the last version of this doc — there is no longer a local JWT/refresh-token session, and no local Company/Member/role model. Identity, sessions, and company membership are entirely owned by MSG91's hosted proxy-auth widget. This API stores none of that itself.

The one credential you'll use

The MSG91 widget hands the frontend a proxy_auth_token (PAT) directly. That PAT is the session — send it as a raw header (not Authorization: Bearer) on every authenticated request: 

proxy_auth_token: <token from the MSG91 widget>

There is no refresh flow, no cookie, and no in-memory access token to juggle — hold onto the PAT itself for the life of the session (same place you'd have kept an access token before) and send it on every call, including GET /auth/me and every /companies/... route. A missing header is 400; a rejected/expired PAT is 401 with code: "PROXY_TOKEN_REJECTED" — send the user back through the MSG91 widget in both cases.

The same PAT also works against the deploy endpoint (ship.embarko.ai) — deploying an app (2026-09-17) and status & logs (2026-09-13). Those calls additionally need X-Company-Id, since a PAT isn't scoped to one company the way a deploy token is. It's one credential for the whole dashboard, across both hosts.

Deploy tokens (a separate credential, not for the frontend to auth with)

Created and listed through this API (see Deploy tokens) so a member can manage them in the dashboard — but the raw token itself is only ever used against the separate deploy endpoint at ship.embarko.ai/apps. The frontend's job is CRUD on token metadata, never using a deploy token to call this API.

The dashboard no longer needs to mint one just to deploy. Since 2026-09-17 the upload path takes the user's own PAT (see Deploy an app), so don't build a flow that silently creates a deploy token behind an upload button — a deploy token is a long-lived, company-wide secret, and one should only exist because a person deliberately asked for one to use outside the browser.

No more roles

There is no company_admin / project_admin / viewer distinction anymore. MSG91 proxy reports membership as a yes/no count, not a role — so any member of a company can do anything scoped to it (create/rename/delete projects, manage tokens, change billing, invite/remove members via the MSG91 embed itself). Don't build role-gated UI against this API; there's nothing here to check.

Membership & invites live on MSG91, not here

There is no /companies/:id/members endpoint in this API anymore. Inviting, listing, and removing members happens through the MSG91 proxy embed the dashboard already hosts for login — this API only reads the resulting membership (via GET /companies and the 404-for-non-members behavior described below), it doesn't manage it.

Errors

Every error is JSON. Validation failures follow one predictable shape everywhere; most other errors carry a stable code string too — prefer branching on code over the human-readable error message where one is present.

400 · validation failed
{
  "error": "Validation failed",
  "details": [
    { "path": "email", "message": "Invalid email" }
  ]
}
everything else (proxy / billing / auth errors)
{ "error": "Add a payment method before choosing a paid plan", "code": "BILLING_PAYMENT_METHOD_REQUIRED" }
StatusMeaning here
200 / 201Success. 201 on every POST that creates a row.
204Success, empty body — every DELETE, plus logout.
400Body failed validation (see shape above), a missing/malformed header, or a code-level reject (e.g. rollback target has no image).
401Missing/invalid/expired proxy_auth_token — code: "PROXY_TOKEN_MISSING" (well, that one's actually 400 — see below) or "PROXY_TOKEN_REJECTED".
402Billing only — a paid plan was requested with no payment method on file (BILLING_PAYMENT_METHOD_REQUIRED).
404The company/project/token/domain/deployment doesn't exist, or you're not a member of that company — the API intentionally doesn't distinguish those two, so it never confirms a company's existence to a non-member.
409Conflict — e.g. a project-name slug that's already taken, a domain already registered elsewhere, billing customer already exists, or already on the requested plan.
422Understood the request, semantically can't do it — e.g. rolling back to a deployment that never succeeded, or a custom domain's DNS not yet pointing at the platform.
502 / 503An upstream service (identity, billing, or the deploy pipeline) failed or was unreachable. Worth a retry; not something the caller did wrong.
500Something broke server-side. Not expected in normal use; worth reporting with the request that triggered it.
PROXY_TOKEN_MISSING (no proxy_auth_token header at all) is actually 400, not 401 — a deliberate distinction so a misconfigured client sees "you forgot to send the header" rather than "your login expired." Only a header that's present-but-rejected is 401.

Auth

Login is the MSG91 widget, not a form this API renders. The frontend embeds MSG91's widget and gets a proxy_auth_token one of two ways — pick one of the two flows below, not both. Either way, the PAT the widget gives you is the thing you hold onto and send on every request afterward (see Auth model).

POST /auth/msg91/exchange token in body, no header needed

Verifies a freshly-obtained proxy_auth_token against MSG91 and makes sure the user's current company has billing set up (best-effort — see billing in the response). Doesn't issue any credential of its own: the PAT you already have is what you use from here on, this endpoint is really just "confirm this PAT works and warm things up."

Request body
{ "token": "<proxy_auth_token from the MSG91 widget>" }
200 Response
{
  "user": { "id": "usr_9f2...", "email": "rita@acme.dev", "name": "Rita Sharma", "isSuperAdmin": false },
  "currentCompany": { "id": "co_4a1...", "name": "Acme Robotics" }, // or null
  "billing": "ready" // or "pending" -> call POST .../billing/customer
}
The frontend keeps using the same proxy_auth_token it POSTed here as its session credential going forward. This endpoint doesn't mint a separate access token.
user.isSuperAdmin is this API's own flag, not MSG91's — never granted or changeable via any API (DB-only, see Admin) — sent so the dashboard can show its admin-only nav/routes conditionally. The /admin/* routes are the actual enforcement point regardless of what a client does with this.
GET /auth/msg91/callback no auth required

The redirect-flow counterpart to exchange — MSG91 redirects the browser here directly with the token in the query string. Verifies it (so bad logins surface as auth_error) and redirects onward. There is no JSON to read — a client on this flow gets its PAT from the proxy embed it already hosts client-side, not from this response.

Query params
ParamType
proxy_auth_tokenstringappended by MSG91 itself
nextstring, optionalwhere to land after login — a path only (e.g. /dashboard); anything off-origin silently falls back to /
302 Redirect (success)
Location: <FRONTEND_ORIGIN>/dashboard
302 Redirect (bad/missing token)
Location: <FRONTEND_ORIGIN>/dashboard?auth_error=invalid_token
POST /auth/logout proxy_auth_token

No body. Drops this API's own identity cache for the PAT so a revoked token isn't served stale from the cache. The frontend must also revoke the PAT against MSG91 itself — this endpoint alone doesn't invalidate it there. 204 on success.

GET /auth/me proxy_auth_token

The logged-in user's full MSG91 identity, merged with their own fuller record. Good for app-boot.

200 Response
{
  "id": "usr_9f2...",
  "email": "rita@acme.dev",
  "name": "Rita Sharma",
  "company": { "id": "co_4a1...", "name": "Acme Robotics" }, // proxy's "current" company, or null
  "isSuperAdmin": false // this API's own flag, see the exchange endpoint's note above
  // ...plus any other fields MSG91 sends on this identity
}
For the full list of companies this user belongs to (not just proxy's "current" one), call GET /companies instead.
POST /auth/switch-company proxy_auth_token

Moves MSG91 proxy's notion of "current company" for this PAT, so the proxy embed (which renders whatever proxy thinks is current) agrees with what the dashboard is showing. This API never reads "current company" itself — every /companies/:companyId/... route scopes from the URL, not from this — so calling it isn't required for the API to work, only for the embed's own UI to stay in sync.

Request body
{ "companyId": "co_4a1..." }
200 Response
{ "companyId": "co_4a1..." }
404 if the caller isn't a member of that company — same membership check every scoped route uses.

Companies

A Company is the account/workspace boundary, owned entirely by MSG91 proxy — this API has no local Company table. Every project and deploy token sits under exactly one company id (a plain proxy id string). Rename, delete, and member management all happen through the MSG91 proxy embed, not through this API.

GET /companies proxy_auth_token

Every company the current user belongs to, straight from proxy — each with a projectCount, same field as get one below.

200 Response
[
  { "id": "co_4a1...", "name": "Acme Robotics", "projectCount": 3 }
]
No role or member-status field on each entry — see Auth model, there's no role concept left. Membership is binary.

Request body
{
  "name": "Acme Robotics",
  "email": "billing@acme.dev" // optional — falls back to your own email for billing
}

Projects

One Project == one deployed app. slug is derived from name at creation — it's the live subdomain and the X-App-Name a deploy uses, unique platform-wide. It can be changed (PATCH …/projects/:projectId/slug); id never changes, and is what a deploy sends as X-App-Id to keep reaching the app. A renamed app keeps its old names: nobody else can claim them, and a deploy under one reaches the app.

POST /companies/:companyId/projects proxy_auth_token

Creates a project row. This doesn't deploy anything by itself — an app becomes live the first time a deploy token for this company is used against ship.embarko.ai/apps with a matching X-App-Name.

Request body
{ "name": "marketing-site" }
201 Response
{
  "id": "prj_7c2...", "companyId": "co_4a1...",
  "slug": "marketing-site", "name": "marketing-site",
  "memoryMb": 256, "isOrphan": false, "orphanExpiresAt": null, "kind": "service",
  "createdAt": "2026-09-07T09:00:00.000Z"
}
409 if the slug is already taken — slugs are unique platform-wide, not just within a company.
GET /companies/:companyId/projects proxy_auth_token

Every project in the company — same field set as get one below, status and health both included new. health is fetched per project in parallel (still a real Nomad call each, just not sequential) — fine at today's expected scale (a handful of projects per company); revisit with pagination if that stops holding.

200 Response
[
  {
    "id": "prj_7c2...", "slug": "marketing-site", "name": "marketing-site",
    "memoryMb": 256, "kind": "service", "appType": "portfolio", "currentDeploymentId": "dep_x8r...",
    "status": "success", // "success" | "failed" | "in_progress" | "no_deployments"
    "health": "running",
    "schedules": { "count": 2, "failing": 0 }
  }
]
status is the current deployment's own status (via currentDeploymentId — see Deployments' isCurrent), not necessarily the most recent row by timestamp: if a deploy attempt after a successful rollback itself fails, that failed attempt is newer, but status here still correctly reflects the rollback that's actually live. "no_deployments" covers a project that exists but has never completed a deploy attempt. health can legitimately disagree with status — see get one's note.
GET /companies/:companyId/projects/:projectId proxy_auth_token

One project's row, with both status (same meaning as the list endpoint above — the current deployment's own status, not a live check) and a live health field reflecting the app's actual running state right now — good for a project detail/status page. The two can legitimately disagree: status: "success" with health: "crashed" means the deploy itself succeeded but the app has since died at runtime.

200 Response
{
  "id": "prj_7c2...", "slug": "marketing-site", "name": "marketing-site",
  "memoryMb": 256, "isOrphan": false, "kind": "service", "appType": "portfolio", "currentDeploymentId": "dep_x8r...",
  "status": "success",
  "health": "running",
  "schedules": { "count": 2, "failing": 0 }
}
health valueMeaning
runningHealthy, actively serving traffic.
startingJust deployed / redeploying, allocation not placed yet.
crashedAllocation failed or was lost — needs attention.
stoppedJob exists but isn't running (rare in normal use).
not_deployedNothing deployed under this slug yet — normal before the first deploy.

PATCH /companies/:companyId/projects/:projectId proxy_auth_token

Display name only — slug never changes after creation.

Request body
{ "name": "Marketing Site (prod)" }
PATCH /companies/:companyId/projects/:projectId/memory proxy_auth_token

Sets the project's memory override (MB). The platform never provisions below the app's own auto-detected technical minimum (e.g. 512MB for an embedded-DB app) even if you set a lower value here — this is a floor-adjustable override, not a hard cap.

Request body
{ "memoryMb": 512 }
Takes effect on the next deploy or rollback for this project, not instantly on a currently-running app — see Known gaps.
Static sites: refused with 409 not_supported_for_static when the project's kind is "static" — nothing runs on the server, so there is no memory to size. The body carries error, code, a next step and links.help (the deploy service's /capabilities/static-sites topic).
DELETE /companies/:companyId/projects/:projectId proxy_auth_token

Tears down the running app (compute, routing, and its built image) before deleting the project row and cascading its deployments/env vars/domains. Best-effort on the teardown — an outage in the deploy pipeline never blocks the project from being deletable; a failed teardown is logged for manual follow-up, not surfaced as a failure to the caller.

Deployments

Populated automatically after every deploy attempt concludes — this is the actual deploy history, not something triggered from here (except rollback, below).

GET /companies/:companyId/projects/:projectId/deployments proxy_auth_token

Full deploy history for the project, newest first — build number, image, memory, status, who/what triggered it.

200 Response
[
  {
    "id": "dep_p9q...", "version": "v5", "appVersion": "2",
    "imageTag": "marketing-site:2", "memoryMb": 512,
    "status": "success", "errorDetail": null,
    "triggeredBy": "rollback:usr_9f2...", // or a deploy token label, for a real build
    "source": "dashboard", "agentName": null, // new — "agent" + e.g. "claude-code" for a token deploy
    "createdAt": "2026-09-07T09:30:44.000Z", "finishedAt": "2026-09-07T09:30:44.000Z",
    "isCurrent": true
  }
]
A rollback (below) shows up here too, as a normal new version — triggeredBy starting with rollback: is the only tell. Use that prefix if the UI wants to badge rollback entries distinctly.
isCurrent marks whichever entry matches the project's own currentDeploymentId (see the Project model) — not necessarily the newest row. If a deploy attempt after a successful rollback itself fails, that failed attempt is newer by timestamp, but the rollback's row stays isCurrent: true — this is what's actually live, which "most recent row" alone can't tell you.
GET /companies/:companyId/projects/:projectId/deployments/:deploymentId new proxy_auth_token

One deployment, by id — what rollback's statusUrl points at (below), so a caller has something to poll directly instead of re-fetching and re-scanning the full history list on every check.

200 Response
// same shape as one entry in GET .../deployments above, including isCurrent
{ "id": "dep_x8r...", "status": "in_progress", "isCurrent": false, /* ... */ }
POST /companies/:companyId/projects/:projectId/deployments/:deploymentId/rollback new proxy_auth_token

One-click rollback: re-points the live app at a past successful deployment's image, with no rebuild — a "pointer flip" that reuses the same no-rebuild config-push path custom domains already use. The project's current custom domains and env vars are kept exactly as they are today — a rollback only changes what code is running, never live config. Recorded as a brand-new deployment with its own next version number, so it shows up in history rather than rewriting it (see the note above). Async, same shape as POST /apps: responds the moment the target image is confirmed to exist — the one thing worth failing fast on — not once it's actually applied, which can take a real, user-visible moment.

Request
// no body — :deploymentId in the URL is the target to roll back to
202 Response
{
  "accepted": true,
  "deploymentId": "dep_x8r...",
  "statusUrl": "/companies/co_.../projects/prj_.../deployments/dep_x8r...",
  "message": "Rollback started. Applying the previous version can take a little while — poll statusUrl until status is no longer \"in_progress\"."
}
StatusWhen
404:deploymentId doesn't belong to this project.
422Target deployment never succeeded, or has no recorded image — nothing to roll back to.
422code: "rollback_image_unavailable" — the target's build image has been pruned (only the last retainCount images per app are kept locally — see Limitations). The response includes retainCount so the caller knows exactly how far back rollback currently reaches. Detected synchronously, before this ever returns 202 — an image-unavailable rollback never looks accepted-then-fails.
502The deploy pipeline was unreachable when asked to accept the rollback. Genuinely transient/unexpected — the image-unavailable case above is the one common, expected failure and never surfaces as 502.
Memory is floored against whichever is higher: the project's current configured memoryMb, or what that specific past deployment actually needed (its own recorded memoryMb) — an old version that needed an embedded-DB memory floor gets that floor back on rollback, even if the project's memory setting has since drifted lower.
Once 202 is returned, poll statusUrl (GET one deployment, below) — its status moves from "in_progress" to "success" or "failed". A failure this late (the image existed, but applying it still failed) is rare, and errorDetail carries the reason.

Env vars

Baked into the container's env block on every deploy, rollback, or custom-domain config push — see the note on memory, same "next apply, not instant" caveat applies here too.

GET /companies/:companyId/projects/:projectId/env-vars proxy_auth_token

All env vars for the project, values included in plaintext (there's no secrets-masking layer here today).

PUT /companies/:companyId/projects/:projectId/env-vars proxy_auth_token

Bulk upsert. Keys must be a valid identifier (letters/digits/underscore, can't start with a digit) — strictly enforced, since it's baked directly into how the running container's environment is generated.

Request body
{ "vars": [ { "key": "API_URL", "value": "https://api.acme.dev" } ] }
Static sites: refused with 409 not_supported_for_static when the project's kind is "static" — nothing runs on the server to read env vars. The same refusal applies to the agent API's PUT /api/apps/:name/env-vars, PUT .../env-vars/:key and POST .../env-vars/apply. GET and DELETE still work.
DELETE /companies/:companyId/projects/:projectId/env-vars/:key proxy_auth_token

Removes one env var by key.

Schedules new

Timed calls into an app. Normally declared in the app's embarko.json, which the deploy reads and which also gives the app its CRON_SECRET; the endpoints below read runs, run them now, and pause or add an alert webhook to one schedule. Deploy token, addressed by app name — no dashboard endpoints yet. A schedule created with POST here also gets CRON_SECRET created if missing; it reaches the running app on the next deploy or env-vars apply. At each due time the platform sends GET <path> to the app's own address, through the same wake-up path a visitor takes, so a sleeping app is woken. Headers: User-Agent: Embarko-Scheduler/1.0 (+https://embarko.ai/docs/schedules), X-Embarko-Schedule-Id, X-Embarko-Run-Id, and Authorization: Bearer <CRON_SECRET> when the app has an env var named CRON_SECRET. 2xx = ok; anything else, a redirect (not followed), or no complete response within 5 minutes (wake-up included) = failed. The first 2KB of the body is kept on the run. One alert email to the app's owner when a schedule starts failing and one when it recovers (not per run), plus the same events to the optional alertWebhookUrl. Limits, same on every plan: 5 schedules per app, at most every 5 minutes, last 100 runs kept. Every endpoint returns the same Schedule shape (see Data models). Spec: docs/schedules.md.

GET /api/apps/:appName/schedules deploy token

All of the app's schedules, oldest first. Response: {schedules: [Schedule], limit}.

POST /api/apps/:appName/schedules deploy token

Creates a schedule. cron is five fields (minute hour day-of-month month day-of-week); @hourly, @daily, @weekly, @monthly, @yearly are accepted and stored expanded. timezone is an IANA name, default "UTC". path must start with /; a query string is allowed. enabled defaults to true. Response: 201 Schedule.

Request body
{
  "cron": "0 9 * * 1-5",
  "timezone": "Asia/Kolkata",
  "path": "/tasks/daily-digest",
  "name": "daily digest",
  "alertWebhookUrl": "https://hooks.slack.com/services/…"
}
Errors: 400 invalid_cron / schedule_too_frequent (any two of the next 60 occurrences under 5 min apart) / invalid_timezone / invalid_path / invalid_alert_webhook (must be public https://; private, loopback and link-local addresses refused) · 409 schedule_limit_reached · 409 not_supported_for_static. alertWebhookUrl is treated as a secret: never returned, only alertWebhook: {set, host}.

GET /api/apps/:appName/schedules/:scheduleId/runs?limit=20&page=1&outcome=&trigger= deploy token

Analytics new

Traffic, errors, latency, and CPU/memory usage for a deployed app, tracked continuously by the platform — not computed on demand. Every range below is one of 24h, 7d, 30d, 90d, or all (default 24h if omitted); an unrecognized value is a 400 validation error, same shape as everywhere else.

"Unavailable" is not "zero traffic"

The analytics pipeline is separate optional infrastructure and can be disabled or unreachable independently of everything else working. Deploy an app new

The upload itself lives on the deploy endpoint (ship.embarko.ai), not this API — same split as status & logs below. It's listed here because, as of 2026-09-17, the dashboard can call it directly with the proxy_auth_token it already holds: an upload button, not a detour through the Tokens page. Nothing about the existing deploy-token path changed, and this API gained no upload endpoint of its own — the tarball goes straight to the deploy service, as it always has.

POST https://ship.embarko.ai/apps proxy_auth_token + X-Company-Id, or a deploy token

Upload a source tarball and deploy it. The same endpoint for the first deploy and every redeploy after — re-upload under the same X-App-Name and it rebuilds in place. Async: it responds as soon as the upload is accepted, then builds in the background; poll GET /apps/:appName/status, or this API's deployment history, to follow it. The build log is the one dashboard screen this API doesn't serve.

Headers the dashboard sends
proxy_auth_token: <the same PAT you send this API>
X-Company-Id:     <the company the user is currently viewing>
X-App-Name:       my-app     // lowercase/digits/dashes, unique platform-wide
X-App-Version:    abc1234    // optional, image tag only
X-App-Type:       portfolio  // optional, what the app is for (≤60 printable ASCII chars)
X-Agent-Name:     claude     // optional, which agent is deploying (≤60 printable ASCII chars); the dashboard sends none
X-App-Id:         cmh1q2w3e… // optional, app.id from an earlier deploy reply; decides the app (2026-10-21)

Body is the source tarball, exactly as the CLI/agent path sends it. X-Company-Id is required because a PAT isn't company-scoped — a person can belong to several companies, so the dashboard has to say which one this app belongs to. It's verified against proxy membership server-side, never taken at face value.

Or a JSON body (2026-09-28): with Content-Type: application/json, send { "appName", "files": [{ "path", "content", "encoding"? }], "version"?, "appType"?, "agentName"? } instead of the tarball. encoding is utf8 (default) or base64. It's packed into the same tarball server-side, so auth, response and errors are identical. It exists for MCP tool calls, which can only carry JSON. Limits: 25 MB, 2000 files. New error codes: invalid_file_path, invalid_file_content, invalid_file_encoding, invalid_json (400), source_too_large, too_many_files (413).

App type (2026-09-29): the optional X-App-Type header (appType in a JSON body) records what the app is for, as a short label: personal website, portfolio, task management, feedback system, and so on. It's stored as the project's appType and doesn't change how the app is built. At most 60 printable ASCII characters, otherwise 400 invalid_app_type. Leaving it out keeps any earlier value. Agents are told to fill it from context or ask the user once; the dashboard doesn't ask.

embarko.json (2026-10-17): an optional file in the app's top folder, read from the upload (any upload path, including a JSON body's files) before the claim: {"$schema": "https://embarko.ai/schema/embarko.json", "schedules": [{cron, path, timezone?, name?}]}. schedules is the app's whole set of schedules: matched by path, listed ones are created or updated (keeping run history), unlisted ones deleted, [] deletes all; no file or no schedules key changes nothing. Refused before any build with 400: invalid_embarko_json (not JSON — line and column given —, not one object, schedules not a list, over 64 KB), secrets_in_embarko_json (a secret-looking key or value; use env vars), or a schedule error (invalid_schedules, invalid_cron, schedule_too_frequent, invalid_timezone, invalid_path, duplicate_schedule_path, schedule_limit_reached), each naming the entry. Applied only when the deploy succeeds. The app gets a CRON_SECRET env var if it has none (never replaced), in the env of this same deploy. The 202 adds schedules: {declared, appliesWhen: "live"} and links.runSchedules; a temporary app deploys, but its reply says schedules: {declared, applied: false, reason}.

App id (2026-10-21): every deploy reply carries app.id, the project's id, plus action ("created" when this deploy made the app, else "updated") and, when something changed outside the deploy, notices: [{code, from, to, detail}]. The deployer keeps the id as "appId" in embarko.json (the skill writes it) or sends it as X-App-Id; the header wins. The file's appId is read for deploy-token deploys only, never for a dashboard upload, which goes to the app the person picked. The app is resolved by id, else by current name, else by old name, and only then created. A renamed app is built under its current name, with notice app_renamed. Errors: 400 invalid_app_id (header) or 400 invalid_embarko_json (file); 404 app_not_found (no such id in the caller's company); 410 app_deleted (that app was deleted; never recreated by id). 409 app_id_mismatch (the id is followed only under the app's current or an old name; any other name means the code was copied to start a new app, so the original is not overwritten). 409 app_name_taken now also covers another app's old name.

Warnings (2026-10-17): problems that don't stop the deploy come back in the 202 as warnings: [{code, detail}], with a sentence in next and links.help: embarko_json_not_at_top (found only in a subfolder), embarko_json_misnamed (.embarko, embarko.yaml…), embarko_json_unknown_keys (ignored), in_process_timer (no schedules in embarko.json and the dependencies list a timer library such as node-cron or APScheduler, whose jobs stop when the app sleeps; the entry adds libraries and the expressions: [{cron, file}] found), schedules_unchanged (the app has schedules, this upload declares none: kept), schedules_on_static_site (not applied).

Agent name (2026-09-29): the optional X-Agent-Name header (agentName in a JSON body) is stored on the new deployment as agentName, next to a source of "dashboard" (PAT) or "agent" (deploy token) that's derived from the credential. Same limits as X-App-Type; otherwise 400 invalid_agent_name. Self-reported, never used for access. The agent API's rollback and env-var apply calls read the same header (a malformed value there is ignored, not rejected).

Reply shape (2026-09-29): every reply from POST /apps, /status and /logs is { status, app, next, links }. next is one instruction for the app's current state; later steps (claim, showcase) appear in later replies, once they apply. links holds every URL in the reply and nothing else carries one: the URLs next refers to, plus feedback on every reply. The app's own address is links.app, present once it's live; app holds no URL. Errors keep error + code and add next + links. App status & logs new

Live on the deploy endpoint (ship.embarko.ai), not this API — same split as the agent customer-query path below, and sharing that same path's one authorization check (updated 2026-09-13 to also accept proxy_auth_token): a request is allowed if the app is still an unclaimed orphan (no credential needed at all), or if the caller presents either a deploy token or a dashboard proxy_auth_token belonging to the app's own company — so someone already logged into the dashboard can check their own app's status/logs directly, without separately minting a deploy token just for that. Build-log fallback (added 2026-09-21): a build that FAILED never produces an allocation, so this endpoint used to return available: false in exactly the case people reach for logs hardest. That output is where a build failure actually names the command that failed (e.g. the missing binary behind an exit code: 127). Runtime logs still win whenever they exist, so a healthy app's response is unchanged, and source is absent on that path.

Customer queries new

One type and a message. type is "platform_bug", "missing_capability", "docs_issue", "unexpected_behavior" or "other" (added 2026-09-29 so agent reports can be triaged by kind), and "feature" / "feedback" are still accepted, which is what the dashboard widget and contact form send. An unknown type is 400 (on the deploy endpoint's path, code: "invalid_feedback_type"). Submissions come through three independent paths that all feed the same store. Submission-only from here; see the admin listing to read them back. Renamed 2026-09-09 from .../feature-requests to .../customer-query on all three paths — same data, same behavior.

Anonymous visitor, no session at all — email is required in the body here since there's no proxy identity to read it from. Same open+rate-limited shape as POST /public/deploy-tokens/request, its own independent rolling-window counters (per-email, per-IP, global) — a burst of queries never affects deploy-token requests or vice versa.

Third path lives on the deploy endpoint, not here

An AI agent (Claude Code, Claude in a chat client, ChatGPT, whatever) can submit a request, piece of feedback, or other query about the app it's deploying — POST /apps/:appName/customer-query on the deploy endpoint (ship.embarko.ai), not this API. Exact same auth as .../status and .../logs above (all three share one check): a deploy token or a dashboard proxy_auth_token is optional, required to match the app's own company once claimed, not needed while it's still an unclaimed orphan. A required X-Agent-Name header records which agent made the request — free text on purpose, so a new agent is never blocked on a code change here to be recognized. Body: {type, message}, same as the paths above. This API never receives a deploy token or proxy_auth_token directly for this path (see the Auth model section) — the deploy endpoint resolves the app to a company and forwards the query here internally.

Self-advertised in every reply (changed 2026-09-29): the old support block on the POST /apps 202 is gone. Instead every reply from POST /apps, /status and /logs, errors included, carries links.feedback — this endpoint once the app exists, the public one (which takes an email) before it does. When a reply's next tells the agent to report something, it spells out the request body and the X-Agent-Name header right there.

Known gaps

Real, current limitations worth knowing before you build UI that assumes otherwise.

Memory & env-var changes apply on the next deploy/rollback, not instantly

PATCH .../memory and PUT/DELETE .../env-vars persist the desired state immediately, but a currently-running app only picks it up the next time it's redeployed — a new deploy, a rollback, or any custom-domain activity on that project (which resyncs the whole config as a side effect). There's no "apply now" button today.

Env var values aren't masked

GET .../env-vars returns raw values including anything a user pasted as a "secret." No separate secrets tier exists yet — treat every value here as visible to anyone with company access.

Analytics "all" range is really "since ~100 days ago"

Raw analytics history is pruned past 100 days to bound storage — there's no separate long-term rollup, so a project's true lifetime history beyond that window isn't available. Don't render all as literally "since this app was first deployed."

Analytics resource-usage history only exists from when this feature shipped

CPU/memory samples come from a background poller that only started running once analytics landed — there's no backfill for time before that, so resourceUsage.series for an older range may start partway through and simply have no earlier points, not zeros.
