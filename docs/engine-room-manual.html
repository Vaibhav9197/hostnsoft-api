TROUBLESHOOTING

When a deploy goes sideways,
here's what actually happened.

Every entry below is a real failure the deploy API has thrown — not a hypothetical. Each one has the exact text you'll see, what's really going on, and how to fix it. Skim it as a human in two minutes, or grep it as an agent in two milliseconds: the readout block in every panel is copy-paste-exact.

low fixed in seconds
medium blocks progress
high your app is down
01

Rejected before the build starts

Caught on arrival — nothing gets built, nothing gets wasted.

422-unsupported-storage.loglow
The Sandbox Reflex
Readout
"error": "Unsupported storage pattern detected" "detail": "This app calls window.storage, an API specific to Claude Artifacts' sandbox. It does not exist outside that environment and will fail at runtime if deployed here as-is."
Diagnosis
The app still reaches for window.storage — an API that only exists inside Claude Artifacts' own sandbox. Caught by a source scan before a single second of build time is spent.
Fix
Swap it for real persistence: SQLite for simple key/value data, or @electric-sql/pglite for anything relational. Redeploy once it's in.
401-unauthorized.loglow
Wrong Papers at the Dock
Readout
{ "error": "Unauthorized", "code": "unauthorized" }
Diagnosis
An Authorization header was sent, but the token on it is dead, wrong, or mistyped. Sending no header at all is fine on purpose — that's an anonymous deploy. A broken one is never quietly waved through as anonymous.
Fix
Confirm the token hasn't been revoked or rotated. Meant to deploy anonymously? Drop the header entirely instead of sending a bad one.
409-app-name-taken.loglow
Someone's Already Standing There
Readout
"error": "App name \"myapp\" is already in use by a different company"
Diagnosis
The app name is also your live subdomain, so it has to be unique across the whole platform, not just your own account.
Fix
Pick a different X-App-Name. If it's genuinely an old orphan deploy of yours, claim it with a real token before its 24h clock runs out.
02

Crashes after a successful build

The build worked. The app didn't stay up.

oom-137.loghigh
The Silent Memory Hog
Readout — from GET .../status & .../logs
Terminated Exit Code: 137, Exit Message: "OOM Killed" Total Restarts = 2
Diagnosis
The app is asking for more memory than it's been allocated (256MB by default). Frequent causes: an embedded database the platform didn't auto-detect, or a development server accidentally shipped as the production start command — those are hungrier than they look.
Fix
PATCH .../memory {"memoryMb": 1024}, then redeploy — or roll back to the current version to push the new ceiling live with no rebuild at all.
crash-loop.loghigh
Stuck in the Brig
Readout
Not Restarting Exceeded allowed attempts 2 in interval 30m0s
Diagnosis
The app crashed, restarted, and crashed again — so the platform stopped trying rather than loop forever. This line is a symptom, never the disease: the real cause is always logged just above it (usually an OOM kill or an uncaught startup exception).
Fix
Pull GET .../logs, find what actually happened before this line, fix that. A fresh deploy resets the attempt counter.
pull-denied.logmedium
Ghost Cargo
Readout
pull access denied for <image>, repository does not exist or may require 'docker login'
Diagnosis
This one's on us, not you — it means the scheduler went looking for the image on a public registry instead of using the one already built locally. Shouldn't happen through normal use of the deploy API.
Fix
Nothing to do on your end — report it with the app name and timestamp.
03

Who's allowed to ask

Ownership, tokens, and domains.

404-status-check.logmedium
Who Goes There
Readout — from GET .../status or .../logs
{ "error": "Not found" }
Diagnosis
These URLs answer to the token from the company that actually owns the app — or to nobody at all, but only while the app is still an unclaimed orphan. The instant it's claimed, the same URL starts asking for papers. A 404 here never confirms the app even exists; that's on purpose.
Fix
Send Authorization: Bearer <your deploy token> for a claimed app. Still meant to be an orphan? Send no header at all.
422-dns-pending.logmedium
Fog Off the Coast
Readout
"error": "DNS does not yet point at the platform — check the instructions below and retry once it propagates"
Diagnosis
The DNS record hasn't propagated yet, or wasn't set exactly as instructed. Nothing wrong on our end.
Fix
Double-check the CNAME/A record matches what POST .../domains returned exactly, wait for propagation, and call .../verify again — safe to retry as many times as you like.
proxied-record.logmedium
The Cloud in the Way
Readout — from the domain's status pill
"Not resolving yet"
Diagnosis
The record in your DNS dashboard looks exactly right — and still doesn't resolve to it. Usual culprit: the record is set to "proxied" at your DNS provider (Cloudflare's orange cloud is the classic one). A proxied record doesn't actually point where it says — it points at the provider's own proxy IPs instead, so there's nothing for us to verify against.
Fix
Switch the record to DNS-only / unproxied (in Cloudflare: click the orange cloud so it turns grey), then hit .../verify again. No real propagation wait — it's a settings change, not a DNS change, so it should pass within a minute or two.
04

Not actually broken

The two "failures" that aren't.

202-accepted.loglow
Where Did My App Go
Readout
HTTP 202 "accepted": true "message": "Deployment accepted and is building in the background..."
Diagnosis
Not a failure — a fresh build can take a few minutes, so the deploy API hands back an acknowledgment immediately instead of making you hold the line for it. Treating 202 as "it's live" is the actual bug here.
Fix
Poll the statusUrl from the response until deploy.status reads success (or failed). Agents especially: 202 means "keep watching," never "done."
524-timeout.logmedium
The Old Complaint
Readout
524: A timeout occurred (the CDN's own error page)
Diagnosis
Historically this fired because the deploy endpoint waited out the entire build before answering, and the proxy in front of it gave up first. That's fixed — the response now comes back long before any of that.
Fix
If it recurs, check upload size/connection first — that's the slow part now, not the build. Still happening on a normal-sized upload? Report it.
05

Rollback

Digging up an old version.

502-rollback-failed.logmedium
Digging Up an Old Wreck
Readout
"error": "Rollback failed: Image \"myapp:1699999999\" is no longer available on this host"
Diagnosis
You asked to roll back to a version whose build has since been cleaned off the host — usually a very old one, or one from before the host was last rebuilt.
Fix
Roll back to a more recent version instead, or redeploy that old source fresh if you still have it.
